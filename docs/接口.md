## 一、阶段目标与交付物

**目标**：把"眼镜和服务器之间怎么说话"定下来，并让两端可以**独立开发、并行推进、互不阻塞**。

**本阶段交付物（4 件，缺一不可）**：

| 编号 | 交付物 | 位置 | 主责 |
|------|--------|------|------|
| D1 | 接口分工与协作说明（本文档） | `接口.md` | 闫 |
| D2 | 接口字段约定 | `API_CONTRACT.md` | 闫 |
| D3 | 服务端接口（先假实现，后接真引擎） | `server/api.py` | 李 |
| D4 | 客户端调用脚本 | `client/mock_client.py` | 闫 |

**整体验收标准**：客户端发一帧画面 → 服务器返回带分割标注的结果 → 客户端能保存/显示该结果。

## 二、角色分工

### 闫 —— 接口定义 + 客户端 + 验收

**负责**
- 主笔并维护 `接口.md`、`API_CONTRACT.md`
- 主持接口评审会，汇总拍板结论
- 编写客户端：`client/mock_client.py`（发帧、收结果、存图）
- 准备测试样例：各模态截图、模糊/反光/黑屏等坏帧（`client/make_test_frames.py`）
- 联调、验收、录 demo

**不负责**
- 不写 `server/` 目录下的服务端代码（由李负责，避免两人改同一文件）

### 李 —— 服务端实现

**负责**
- 搭建 `server/` 目录与 FastAPI 骨架
- 先实现 `/api/v1/frame` 的**假实现**（返回固定图片），保证客户端当天可联调
- 再将假实现替换为真实引擎（模态分类 → YOLO 检测 → SAM2 分割/跟踪）
- 配合联调、修复服务端问题

**不负责**
- 不直接编辑 `接口.md`、`API_CONTRACT.md`（有意见提给闫，由闫统一修改）

### 师兄 / 第三人（若团队有）

**负责**
- 接口方案评审、技术风险提示
- 眼镜型号调研（不占关键路径，可并行）
- **不参与**同一文件的编辑，避免冲突

### 导师

**负责**
- 评审接口方案、拍板关键决策、验收阶段 demo、协调硬件资源

## 五、协作规则

1. **接口冻结机制**
   - 冻结前（T8 之前）：字段可自由调整，改完同步对方即可
   - 冻结后：任何字段变更必须走「提出 → 双方确认 → 更新 `API_CONTRACT.md` → 通知对方」，禁止口头改完不更新文档

2. **假实现先行原则**
   - 服务端任何接口，先给"能返回固定数据"的假实现，让客户端能立刻联调
   - 假实现换真实现时，**接口签名和字段不得改变**

3. **沟通约定**
   - 接口相关变更**必须发群消息**，不能只在私下改代码
   - 卡住超过 2 小时无法推进 → 在群里说明卡点，必要时找师兄/导师

4. **禁止事项**
   - 禁止两人同时编辑同一文件
   - 禁止修改 `scripts/` 下现有引擎（只复用）
   - 禁止在未更新文档的情况下改接口字段

## 六、任务如何交付与验收

### 交付格式（每次交付统一按这三条说明）

1. **文件在哪**：给出路径，如 `server/api.py`
2. **一句话说明**：这个文件能做什么
3. **怎么验证**：给出可直接复制运行的命令

示例：
> 交付：`server/api.py` 假实现
> 说明：接收一帧 jpg，返回固定结果的 JSON
> 验证：`curl.exe -F "session_id=test" -F "image=@test.jpg" http://127.0.0.1:8000/api/v1/frame`

### 交付前自检清单

- [ ] 代码能跑通，不报错
- [ ] 按上面三条格式写清交付说明
- [ ] 自己先验证一遍（提供可复现命令）
- [ ] 涉及接口字段的，已同步更新 `API_CONTRACT.md`

### 验收方式

| 交付物 | 验收人 | 验收动作 |
|--------|--------|----------|
| 服务端接口 | 闫 | 用客户端脚本真实调用一次，能拿到正确结构的结果 |
| 客户端脚本 | 李 | 在服务端日志确认收到请求、参数完整 |
| 接口文档 | 双方 + 导师 | 逐条确认字段无歧义 |

### 联调标准流程

1. 李启动服务：`python server/api.py`（或 uvicorn 命令），确认打印监听地址
2. 闫运行客户端：`python client/mock_client.py --image <测试图>`
3. 检查两点：客户端拿到的 JSON 字段齐全 + 结果图已保存
4. 任何不一致：**以 `API_CONTRACT.md` 为准**，谁错谁改
5. 联调结果与问题记录到本文档"变更记录"下方的问题区

## 九、已定决议（v0.2，可直接开发）

> 原 v0.1 的 4 个待拍板问题已全部定死，**不需要再开会讨论，直接照着做**。字段细节见 `API_CONTRACT.md`。

### 9.1 四个核心决策

| # | 议题 | 决定 | 理由 |
|---|------|------|------|
| 1 | 画面怎么传 | **multipart 文件上传 jpg**（长边 ≤1280、≤300 KB） | 比 base64 省约 1/3 体积，两端都原生支持 |
| 2 | 结果怎么回 | **回整张 overlay 图**（base64 内嵌 JSON） | 客户端零叠加逻辑，眼镜端算力省 |
| 3 | 通信方式 | **纯 HTTP 一问一答** | 最好调试，出问题一眼看得出；WebSocket 留后期 |
| 4 | 服务器怎么"反问" | `need_confirm=true` + `message` + `candidates` | 复用已有字段，客户端弹提示即可 |

### 9.2 接口范围收敛

- **本期只做 2 个接口**：`A1 /api/v1/frame`（画面）、`A2 /api/v1/audio`（语音）
- `A3 状态查询`、`A4 WebSocket` **暂缓**——A1 的响应已带回模态、目标、提示，客户端自己存状态即可

### 9.3 行为语义（最容易被忽略、漏了必返工）

| 事项 | 决定 |
|------|------|
| `session_id` | 客户端生成，一次医生使用一个，30 分钟无请求服务器可清理 |
| 目标切换 | **只有语音显式指令能切**，画面出现新目标不自动切 |
| 模态切换 | 连续 3 帧分类一致才切；低置信度保持原模态（防抖动） |
| 帧率 | 5 fps；上一帧未返回不发新帧；服务器丢旧帧不排队 |
| 超时重试 | 3 s 超时，不自动重试，连续失败 3 次暂停并提示 |
| 错误码 | 6 个：1001 参数错 / 1002 无会话 / 2001 画面不可用 / 2002 未识别模态 / 2003 需澄清 / 5000 内部错误 |

### 9.4 待导师 / 硬件确认的 4 项（已给暂定假设，**不阻塞开发**）

| 事项 | 暂定假设 |
|------|----------|
| 眼镜型号与接口 | 假设能拿到一帧图像（UVC / RTSP）；开发期用笔记本摄像头、手机模拟 |
| 服务器放哪 | 假设本地 RTX 5060，局域网访问 |
| 回显介质 | 假设手机 / 副屏；AR 镜片作为可选增强 |
| 数据合规 | 假设只用公开数据集，不接触真实患者数据 |

> 这 4 项只需**问导师要个确认**，不影响你们今天开始写代码；真答案变了，也只改采集/显示适配层，接口字段不动。
