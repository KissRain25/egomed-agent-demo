# EgoMed-Agent 部署前检查清单

> 适用：把 EgoMed-Agent 部署到一台**新机器**（演示机 / 验收机 / 课题组另一台电脑）
> 版本口径：软件 v0.2.0，接口契约 v1.0.4
> 用法：从上往下逐项打勾，**任一项不过就不要往下走**。所有命令都在项目根目录执行。

## 1. 硬件（最先查，最容易翻车）

- [ ] **独立显存 ≥ 8 GB**（本项目在 RTX 5060 Laptop 8 GB 上验证）
- [ ] **启动前整卡显存余量 ≥ 5 GB**
      ```powershell
      nvidia-smi --query-gpu=memory.used,memory.total --format=csv,noheader
      ```
      > 实测组成：桌面常驻程序 ~1.0 GB + ASR（Whisper medium）~1.9 GB +
      > YOLO/SAM2 ~1.1~1.8 GB ≈ **启动后即占 4 GB**。
      > 8 GB 卡若不腾环境，跑 20 分钟就会因显存触顶把单帧推理拖到 200 秒级
      > （见 `docs/显存分析与建议.md`）。
- [ ] **演示前关闭占 GPU 的常驻程序**：Wallpaper Engine、浏览器后台标签/WebView、
      NVIDIA Overlay、录屏软件、其他训练/推理进程
- [ ] 内存 ≥ 16 GB（服务端 RSS 实测约 2.6 GB，打包/编码另有开销）
- [ ] 磁盘可用 ≥ 20 GB（权重 0.58 GB + 数据数 GB + 运行产物）

## 6. 部署步骤（按序执行）

```bat
1) 安装环境.bat                  :: 建 egomed 环境（已有环境可跳过）
2) egomed.bat doctor             :: 环境自检，返回码 0 才继续
3) egomed.bat check              :: 详细检查（十余项）
4) egomed.bat warmup             :: 预热 ASR（吃掉冷启动，约 60~100s）
5) egomed.bat regress            :: 回归（mock + real）
6) egomed.bat demo               :: 正式演示：起服务端 → 开现场控制台
```

- [ ] 第 4 步 `warmup` 必须成功（否则第一次语音请求会等 60~100 秒，现场很尴尬）
      > ASR 未就绪时服务端会返回 `503 asr_warming`，客户端按 10 秒节奏自动重试，
      > 上限 300 秒 —— 门控是**兜底**，不是常态。

## 8. 常见故障对照

| 现象 | 错误码 | 下一步 |
|---|---|---|
| 起不来，提示端口被占 | E1002 | 换端口或关掉占用 8000 的程序 |
| 起不来，提示服务端已在跑 | E3003 | 直接复用已在跑的服务端，或先停掉它 |
| 首次语音要等一分多钟 | — | 服务端在加载 Whisper，属于冷启动；跑 `egomed.bat warmup` |
| A2 返回 `503 asr_warming` | — | 正常，客户端会自动重试；若持续超过 300s 说明 ASR 初始化失败 |
| 分割报「画面里没检测到目标」 | — | 对准屏幕、确认选的模态与画面一致 |
| 越跑越慢、单帧几秒到几分钟 | — | **显存触顶**，先腾显存，见第 1 节 |
| 报「YOLO 权重中找不到目标」 | — | 缺对应模态的 `best.pt`，见第 3 节 |

完整错误码表：`软件制作/错误码.md`（每个码都有「一句人话 + 一条下一步」）。

## 11. 服务端加固后的行为变化（2026-11-03，v0.2.1）

> 部署方如果用的是 **0.2.1 之前**的服务端，这一节有 4 条行为差异需要知道。

| 变化 | 现象 | 客户端/部署方要做什么 |
|---|---|---|
| **ASR 预热门控真正生效** | 真引擎刚启动、ASR 推理路径还没热好时，A2 返回 **503 + `state=asr_warming`**（而不是像以前那样卡住 60~180 秒） | 客户端已内置按 `retry_after_s`（10s）重试同一段录音；**自研客户端要照 A.12 实现**，否则第一句话会被丢掉 |
| **ASR 内部故障不再伪装成功** | ASR 真正报错时返回 **HTTP 500 + code 5000**（以前返回 200 + `status:"ok"`，客户端会当成"没听清"） | 按普通故障处理（提示重试），别再当成功 |
| **预热失败会明确报出来** | `/healthz` 返回 **503 + `state=failed`** + `warmup_error`（以前无论成败都报 200，故障推迟到发第一帧才变 500） | 启动自检时若看到 `state=failed`，直接看 `warmup_error`，不要等请求报错 |
| **画面不可用不再返回 400** | 上传空文件/坏画面返回 **200 + `status:"ok"` + 空字段 + `"画面里没检测到目标，请对准屏幕"`**（以前返回 400 + code 2001，违反契约） | 按契约 A1 边界 1 处理：**保留上一帧回显**，不要清屏 |

另有两项**资源治理**（对部署方是好事，不用做什么）：

- 落盘产物会自动裁剪（每个会话的 `seg/` 只留最近 5 张 overlay + 5 张 mask、录音只留 3 段），
  会话超 30 分钟闲置后目录一并删除 —— 不会再出现"跑几场长稳磁盘涨几百 MB"；
  日志 `runs/server_log.txt` 改为滚动写（单文件 10 MB，保留 3 份历史）。
- 上传体积有硬上限（图片/音频各 2 MB），超了返回 1001。正常客户端压缩后远小于此。

还有一处**内容语义变化**（v1.0.6 决议 #16，字段名/类型不变）：

| 变化 | 旧 | 新 |
|---|---|---|
| `candidates`（需要澄清时） | 目标名，如 `["LV cavity", "Left Ventricle"]` | **模态名**，如 `["ACDC (MRI 心脏)", "CAMUS (超声 心脏)"]` |
| 澄清 `message` | 一律说"在多个模态里都存在" | 跨模态歧义才说模态歧义；一次说多个器官时说"识别到多个目标：左肾、肝…（都在 CT 腹部 里）" |

→ 客户端若把 `candidates` 显示给医生看，**现在显示的是模态名而不是内部类名**；
若你的代码拿 `candidates` 去匹配目标名/类名，需要改成匹配模态名（或只用 `message`）。

## 13. N48 帧级模态自动识别的行为（2026-11-04，v0.2.4 / 契约 v1.0.7）

**这套行为只有一条目的：医生还没说话时，系统先告诉他"这是哪张片子"。**

| 场景 | 服务端返回 | 客户端该显示什么 |
|------|-----------|----------------|
| 已用语音设了目标 | `modality` = 该目标所属模态、`target` = 目标名、`overlay` = 结果图 | 原样显示（**这一路完全没变**） |
| **还没设目标，画面能认出模态** | `modality` = 自动识别的模态名，`target` = `""`，`overlay` = `""` | 显示**模态名 + "看起来是XX，请说要看哪个器官"**；**不要**当成异常 |
| 还没设目标、画面认不出 | 三个字段全空，`message` = "请先告诉我要分割哪个器官（按住说话）" | 显示这句提示，等医生说话 |
| 已设目标、但画面里没有可分割的东西 | 三个字段全空，`message` = "画面里没检测到目标，请对准屏幕" | 显示这句 + 保留上一帧画面 |

要点（部署方/客户端开发者看这里）：

- **`modality` 有值而 `target` 为空，是合法组合**，表示"已认出是哪个模态，等医生说器官"。
- **判不出就不给假结果**：置信度不足、画面不是影像、分类器不可用，一律回落到"请先告诉我要分割哪个器官"，
  **绝不显示一个猜出来的模态**。阈值 **0.85**（离线评测实测确定：纯影像帧判对 100%，
  但"手机拍屏幕"的实拍照片会被误判成 MRI 且提高分辨率无效 → 属缺训练样本，不是阈值能解决的）。
- **连续 3 帧结果一致才切换**（防抖），避免画面抖动导致模态来回跳。
- **已设目标时服务端不跑分类器** → 这条链路**零额外开销**，也不影响分割结果。
- 自动识别结果**只是提示**，真正决定分割哪个模态的仍然是语音设目标那条老路 → **识别错了不影响分割正确性**。
- **字段名、类型、HTTP 路径、错误码、状态码、A1 的 11 个字段全部没变** → 旧客户端**零改动**。

## 14. N50 延迟口径与实测值（2026-11-04，v0.2.4）

**口径（别搞混）**：目标是 **A1 客户端往返 P95**（`client/eval_latency.py` 量的"上传帧 → 收到 overlay"），
**与服务端自报的 `elapsed_ms` 不是一回事** —— 两者都要记，**不要拿服务端自报数字冒充端到端**。

当前实测（五模态各 12 帧，客户端往返口径）：

| 模态 | P95 |
|------|-----|
| ACDC (MRI 心脏) | 394 ms |
| CAMUS (超声 心脏) | 402 ms |
| Amos (CT 腹部) | 94 ms ※ |
| Montgomery (X 光胸片) | 397 ms |
| PolypGen (内窥镜) | 426 ms |
| **五模态合并** | **P95 390~426 ms / 均值 336 ms**（优化前合并 P95 **622 ms**） |

※ **Amos 的 94ms 是"没检出目标"的快速路径**，不代表 CT 分割达标（该模态 YOLO 检不出 spleen，属既有问题）。

**测延迟前必须腾空 GPU**：外部程序占用 GPU 会让语音推理从 0.6s 拖到 88~144s，导致整片假失败
（上次实测：外部程序占 7086/8151 MiB、98% 利用率时，ASR 单句 88.9s > 客户端 30s 超时 → 8 条语音全判失败；
关掉后同一份代码 10/10 PASS）。**这是环境问题，不是代码缺陷**，别写进报告当 bug。

**剩余瓶颈在 GPU 计算本身**（cProfile 证明：`Tensor.to()` 183ms/轮 = 等 GPU 的同步点，不是 CPU 计算）。
要再压到 400ms 以下只剩下的手段是"降精度换速度"（如 YOLO `imgsz` 1024→640），
**必须附 Dice 对照并由负责人拍板**，不擅自改。

## 15. `egomed.exe` —— 双击即用的入口（2026-11-04，v0.2.4）

**交付方拿到的东西有两种启动方式，用哪种取决于目标机器有没有 Python 环境**：

| 情况 | 用哪个 | 说明 |
|---|---|---|
| 目标机器**没装 Python** | `egomed.exe` | 双击即开界面、跑自检、生成诊断包、读写配置（**界面层零依赖**） |
| 要**真跑分割推理** | `egomed.bat` / `python launcher.py` | 推理依赖 torch+CUDA+SAM2（>2.5GB），**不在 exe 里**，仍需 egomed 环境 |

- **exe 版本信息**：`egomed 0.2.4 (contract v1.0.7)`（已实测，无 BOM）
- **exe 放哪**：放在**项目根目录**（或便携包根）→ 它靠"exe 旁边的目录"定位项目根，`client/`、`VERSION`、`configs/` 都要在旁边
- **自检怎么读**：`doctor` 里「依赖：torch 不在 exe 内（推理跑在服务端环境里，属正常）」是**正常提示**，不是故障；
  真正要管的是 `E3001`（没找到解释器）/ `E3002`（缺依赖）/ `E3004`（缺权重）
- **重新打包**：`python scripts/build_exe.py`（详见 `docs/交付形态与exe说明.md`，含两个 conda 打包坑的记录）

## 12. `/healthz` 新增两个运维计数（2026-11-03，v0.2.3）

`/healthz` 是**非契约**运维接口（契约 P2.11 白名单），加字段**不影响契约版本**，老客户端可忽略。

| 新字段 | 含义 | 怎么用 |
|---|---|---|
| `dropped_frames` | 服务端侧被新帧覆盖而丢弃的帧数（latest-wins 丢帧语义累计） | 判断"发帧太快、客户端太超前"；真引擎下才会增长（假实现没有丢帧语义） |
| `client_gone` | 帧算完了、但客户端已经断开（多半是客户端 3s 超时后关了连接） | 判断"客户端超时率"。持续增长 = 客户端超时太紧或服务端单帧太慢 |

原字段全部保留：`status` / `sessions` / `real_engine` / `state` / `rss_mb` / `gpu_mem_mb`
（`state=failed` 时另有 `warmup_error`）。

> ⚠️ **客户端口径变化（v0.2.3）**：直播客户端的**延迟统计只收服务端正常应答**，
> 超时的请求**不再计入** P95/均值（以前 3000ms 超时被当成"服务端延迟 3000ms"，P95 直接被顶满），
> 超时次数改为**单列** `请求超时` 一项。「结果刷新率」也改成按**服务端正常应答的帧数**算，
> 不再把"发出去但没回应的请求"算成刷了一帧。**接口本身零变化。**
