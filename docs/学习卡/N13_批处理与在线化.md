# 学习卡：N13 —— 批处理内核 vs 在线化需求

> 生成：2026-09-22 ｜ 关联：`docs/联调发现_20260920_真引擎实时链路.md` §六之二、`server/api.py`
> 用途：复习 / 答辩 / 给新队友讲“为什么复现的算法不能直接上线”

---

## 一、术语

| 术语 | 一句话 |
|------|--------|
| **批处理（offline/batch）** | 一次拿到整段数据统一计算，追求结果最准，允许慢 |
| **在线（online/streaming）** | 每次只拿到一帧/一小段，要求单次响应快，追求“按时出结果” |
| **滚动窗口（rolling window）** | 只保留最近 N 帧作为上下文；N 越大越稳、越慢 |
| **时序滤波（temporal filtering）** | 用“连续多帧出现”来抑制误检，如 `min_occurrence=2` |
| **掩膜传播（mask propagation）** | SAM2 用 memory attention 把第 1 帧的掩膜延续到后续帧 |
| **延迟预算 / P95** | 契约规定“首次点名 ≤1.5s、跟踪帧 ≤200ms”；看分位数而非均值 |
| **latest-wins 丢帧** | 队列=1，新帧覆盖旧帧——实时场景丢弃过期帧优于排队 |
| **预热（warmup）** | 启动时先加载模型，避免首个请求承担 30~60s 冷启动 |

## 二、原理一句话

> **复现来的算法假设“数据是整段给的”，一旦搬进实时链路，这个假设就碎了**——于是出现两类症状：**时序滤波把单帧结果全滤掉**（首帧必空）、**窗口越满算得越久**（延迟随会话线性增长）。

## 三、两个缺陷的正解

| 缺陷 | 根因 | 修法 | 原理名称 |
|------|------|------|---------|
| 首帧必空 | `min_occurrence=2` 需要“后续帧”作前提，单帧场景前提不成立 | 显式传 `min_occurrence=1` | 滤波器的**隐性前提**被使用场景破坏 |
| 延迟随会话增长 | 每次请求对整个窗口重跑检测+SAM2+跟踪，计算量 ∝ 窗口帧数 | 窗口 10→1，只推理最新帧（方案 B） | **批处理 → 在线化**：把复杂度从 O(N) 变 O(1) |

## 四、答辩能讲什么（可直接用的话术）

> “我们的算法内核复现自离线批处理流程，它默认‘整段视频一起算’。接入实时链路后暴露两个问题：时序滤波导致首帧无结果、滚动窗口导致延迟随会话线性增长（1.4s→3.8s，突破 3s 超时）。我们把窗口降到单帧、显式放宽滤波参数后，P95 从 3035ms 降到 491ms、超时从 7 次降到 0——**核心思路是把在线推理的复杂度从与窗口线性相关变为常数**。代价是失去跨帧传播，画面快速移动时掩膜可能抖动，这是静态阅片场景下可接受的折中。”

## 五、踩过的坑

| 坑 | 教训 |
|----|------|
| 只测 4 帧就断定“检测器零检出”（N14 初判） | 采样不足会得出错误结论，**先扩大采样再下判断** |
| 验收脚本只断言延迟，掩盖了“全程返空” | **断言维度决定你能发现什么** |
| 假实现坏帧阈值对分辨率敏感（N16） | 阈值型指标有分辨率/模态依赖，跨尺寸复用前必须归一化 |
| 首帧延迟达标 ≠ 首帧有结果 | P0.2 当时只测了耗时，没测有没有产出——**指标要成对设计** |

## 六、可复用的判断清单（遇到类似问题照着问）

1. 这段算法的**隐式假设**是什么？（整段数据？连续帧？稳定输入？）
2. 每次请求的计算量是**常数**还是随某个量增长？
3. 我的指标测的是**耗时**还是**产出**？两者都要测。
4. 改完能不能**一条命令复现对比**？不能复现的改动不要提交。
5. 有没有**回退路径**（备份/开关）？
