## 第 3 页｜论文复现：五数据集 Dice + 三条发现 — **4 分钟（本页最重）**

**本页任务**：用同口径数据证明"复现是认真的"，并**把三条发现讲透**（尤其"一个实现细节值 0.75 Dice"）。

### ① 口径（先说，30 秒）

> 这页是论文主表（Table II）的复现。先说口径 —— 这是"可比"的前提：**同一份评测计划表（438 个无歧义键）、同一套 Dice 定义与两级聚合、完整帧序列、同一个阈值 τ₂ = 0.6**。所以这些数字是**同口径可比**的实现结果，不是随便跑的。

### ② 结果（30 秒）

> ACDC 三类（右心室 0.576、心肌 0.518、左心室 0.777）、Montgomery 双肺 0.691 / 0.674、CAMUS 三类、PolypGen 息肉 0.635、Amos 五个器官。**总体类别宏平均 0.5453，帧加权 0.5174，覆盖 74,184 帧。**

### ③ 三件主动交代（40 秒）

> **一，表中是"原样复现"值**（下面第三条会讲 CAMUS 心肌）。
> **二，Amos 只做到 24/49 例** —— 那 25 个测试病例的标注**没有随数据集发布**（8 个分片我们全下载了，远端确实没有），不是我们没跑。
> **三，论文 README 写的平均是 71.34%，但论文的聚合口径没有公开** —— 所以不做直接对比；补上论文 Table II 原文，就能逐行对齐。

### ④ 三条发现（**2 分钟，本页重点**）

> **第一条：数据完整性直接决定结论。** 我们本地帧只下到每例前 1/3 的时候，X 光双肺 Dice 只有 **0.22**；补齐到完整序列后是 **0.69 —— 差 2~3 倍**，标准差也从 0.09 降到 0.04。教训是：**先核对数据完整性，再比数字。**
>
> **第二条：CAMUS 心肌 ≈ 0 是一个实现细节。** 预测的左心室腔掩膜把心肌环一起包住了（GT 心肌的 **98.5%** 落在预测 LV 里面，预测面积是 GT 的 **2.55 倍**），而最终标签图是**按类别编号升序写入、后写的覆盖先写的** —— 结果心肌被抹掉了。我们把写序改成"心肌优先"后，**全 24 例实测：心肌 0.0018 → 0.7507、LV 还涨了 0.044、LA 基本不变**；CAMUS 类内平均 0.366 → 0.630，五集宏平均 0.545 → 0.602。
> 换句话说：**一个纯实现细节，值 0.75 的 Dice。**
> **而且我们没有过度归因**：用同样方法诊断 ACDC（它的类别顺序同样让 LV 最后写），实测**预测心肌面积是 GT 的 93.2%、LV 掩膜 0.99 倍** → **否证**。所以结论是**条件性**的：**只有"预测掩膜严重外扩"时（CAMUS 是 2.55 倍），写序才会致命**；ACDC 的 0.518 是薄环分割与跟踪漂移的真实难度。这一点我们最想向论文作者确认。
>
> **第三条：Amos 有 25 个测试病例的标注没随数据集发布**（8 个分片全部下载完成、远端无其它来源），所以只能报 24 例子集 —— **建议向作者索取这批 GT。**

### ⑤ 结论（20 秒）

> 结论：**评测协议层已经完全对齐**（同一计划表、同一 Dice 定义、同一两级聚合、同一激活帧），差异只可能来自**实现细节**和**数据覆盖**；补上论文 Table II 原文，"指标复现"这一项就能闭环。

## 第 4 页｜设计流程（一）：三层职责 — 1.5 分钟

**本页任务**：讲清「眼镜端零智能、服务器全处理」这个核心架构决策。

> 这张图是整个系统的分工。
>
> **左列是眼镜端，核心一句话：零智能。** 只做四件事：采集画面、按规格压缩（长边 1280、JPEG 质量 80、单帧不超过 300KB）、发出去、把结果回显。另加两件保障体验的事：**抽帧节奏**（默认 5 fps）和**断流自动重连**；再加坏帧时的**"保留上一帧"防抖**。**本地不跑任何模型。**
>
> **中间是通信，也就是接口契约**，已冻结到 v1.0.3：只有两条链路 —— **A1 传画面、返分割结果；A2 传语音、返目标**，全部 HTTP 一问一答。**冻结的意思是：只允许加字段，不允许改名改语义；要改必须走"提出→双方确认→改文档→通知"的流程。**
>
> **右列是服务器，所有计算都在这儿**：模态识别 → YOLO 检测 → SAM2 分割 → 回显图；语音侧是医学谐音优化的 ASR → NLU 解析目标。三个工程细节很关键：**丢帧语义只算最新帧**、**坏帧 / 歧义 / 小器官三类边界都有明确处理**、**启动预热让首帧立即出结果**。
>
> 落点：**眼镜端零智能 → 模型升级不动眼镜，换硬件只改适配层。**

**过渡**："那具体一次交互怎么走？"

## 第 5 页｜设计流程（二）：一次交互怎么走 — 1.5 分钟

**本页任务**：用 5 步讲明白"医生说一句，画面就按新目标分割"。

> 五步：
>
> ① 医生看着屏幕说"分割左肺"，客户端把录音发给 **A2**，**约 0.5 秒**返回目标 `left lung`；
> ② 客户端在**后台线程**持续上传画面，**抽帧 2~3 fps**；
> ③ 服务器**用目标反推模态**（这点很重要：模态不是每帧分类出来的，而是由目标推出来的），然后检测 + 分割，返回叠加结果；
> ④ 客户端把"原始画面 + 分割结果 + 状态提示"一起显示（HUD）；
> ⑤ 医生转头或被遮挡 → 服务端判定**坏帧**、返回空结果并给提示语，客户端**保留上一帧、不闪跳**，拿开后自动恢复。
>
> 六条设计决策里强调三条：**接口先冻结，两端才能独立开发**；**丢帧语义只留最新帧、绝不排队**（实时性的关键）；**坏帧返空、宁可重拍也不猜**。

**过渡**："有设计就要有数据 —— 下面是实测。"

> **延迟 P95 512 毫秒、0 错误、首帧即出结果**；
> **提交节奏 2.77 fps**（刷新 2.56 fps），手机当镜头连续采集 90 秒；

## 第 8 页｜软件进度与两周目标 — 1 分钟

**本页任务**：用"**软件做到哪一步**"的口径讲进度与下一步（不列工程任务，讲用户能感知的变化）。

> **左边是现在已经能用的**（演示原型）：
> - 手机 / 摄像头当"眼镜镜头" → **实时分割回显**；
> - **说一句就切目标**（"分割左肺" → 下一帧就按左肺分割）；
> - 遮挡不闪跳、拿开自动恢复；
> - **一键启动 + 一键验收**（假实现 8/8、真引擎 11/11）；
> - 真机实测：**2.77 fps · P95 512ms · 0 错误**。
>
> **右边是两周后想达到的**（更好用）—— 每条都是**能看出来**的变化：
> 1. **开口前就有结果** —— 不用先说"分割左肺"，系统自己判断影像种类；
> 2. **启动就知道能不能用** —— 自动做机位自检，不合适直接提示"请对准屏幕"；
> 3. **边说边比划不偶发失败** —— 修掉"说话改目标"与"发画面"撞一起时的 1.7% 超时；
> 4. **旁人说话不误触发** —— 语音加门槛（太短 / 太轻 / 不像指令的直接忽略）；
> 5. **标注更跟手** —— 减少镜头移动时的漂移；
> 6. **知道几人能同时用** —— 并发压测 2~4 人，测出上限；
> 7. **单帧更快** —— 先量出 500ms 花在哪一段，再针对性优化。
>
> 另有**内部整理**：CAMUS 心肌"写序修复"开关转正 + 加回归测试（防结论丢失、交接踩坑）。
>
> 说明：按空闲时间推进，**不承诺完成时间**；每一项都以"**真机可验证**"为准。

## 附一｜常见提问应答（背这几条就够）

| 可能被问 | 怎么答 |
|---------|--------|
| 为什么不在眼镜上跑模型？ | 零智能设计：眼镜要极轻、任何 AR 眼镜都能接、模型升级不动硬件；代价是强依赖网络 |
| 为什么只有 2~3 fps？ | 服务端单帧约 500ms，这是算力上限；不抽帧反而更糟（改造前 5 帧要 8.75s 才返完，延迟越堆越高）。现状"够看屏幕说话，不够掩膜跟手" |
| 模态怎么识别？ | 当前是"语音定目标 → 反推模态"；帧级分类挂 v1.x。契约已规定"连续 3 帧一致才切换"的防抖 |
| 坏帧为什么不报错？ | 坏帧是日常常态（转头/遮挡），契约用 `200` + 空字段表达，让客户端优雅降级（保留上帧 + 提示） |
| CAMUS 心肌为什么能差 0.75？ | 标签图按类别编号升序写入、后写覆盖先写；CAMUS 的 LV 掩膜外扩到 GT 的 2.55 倍，把心肌环整块包住 → 心肌被抹掉。改成"心肌优先"后 0.7507；ACDC 已实测否证（掩膜 0.99 倍）→ 属**条件性**问题 |
| 与论文 71.34% 差在哪？ | 三处：CAMUS 心肌（已定位为写序）、Amos 只 24/49 可达、论文聚合口径未公开 |
| 现在能演示吗？ | 能。双击 `启动模拟眼镜.bat`，预热约 78 秒，之后手机/摄像头当镜头即可实时演示；也有成品演示视频 |
| 怎么分工的？ | 我：客户端 + 接口契约 + 评测复现；李：服务端引擎接入与优化 |
