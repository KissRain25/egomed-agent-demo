## 一、背景：客户端实时链路已跑通，暴露两个服务端问题

客户端 `client/live_client.py`（N4）已交付并实测。在真实链路下发现：

**问题 ①：任何会话的第一帧必然返空**
`server/api.py` 的 `_handle_frame_real()` 调用 `demo._segment_target(...)` 时使用默认参数，其中
`min_occurrence=2`（**同一目标需连续出现 ≥2 帧才保留检测**）。
首帧窗口只有 1 帧 → 检测被过滤 → 返回 `overlay=""` + "画面里没检测到目标"。
实测：X 光样例第 1 帧空（79 ms），第 2 帧起正常（1.29 MB overlay）。

**问题 ②：A1 延迟随会话窗口增长，突破 3s 超时**
`WINDOW_SIZE = 10`，且**每次请求都对整个滚动窗口重跑"检测 + SAM2 分割 + 跟踪"**（等同离线批处理模式），窗口越满越慢：

| 会话窗口内帧数 | A1 实测耗时 |
|---------------|------------|
| 2 帧 | 1361 ms |
| 3 帧 | 1547 ms |
| 6 帧 | 3387 ms |
| 窗口满（10 帧） | 2568~3830 ms（ACDC 目标 myocardium 实测） |

后果：客户端 `TIMEOUT=3.0s`，超时被丢弃（实测 12 帧内 HTTP 超时 7 次），有效发帧率掉到 0.42 fps，实时性不成立。

## 二、需要改什么（两处，都在 `_handle_frame_real` 相关路径）

### 改动 1：首帧放宽滤波（必做，约 5 行）

窗口帧数不足 2 时，不要把检测结果全滤掉：

```python
# _handle_frame_real() 中调用 _segment_target 处
window_n = len(image_files)          # 当前窗口实际帧数
result = demo._segment_target(
    predictor, yolo_model, image_files, fdir, target_id,
    id_to_name, class_id_to_gray, out_dir, target,
    min_occurrence=1 if window_n < 3 else 2,   # ← 首帧/少帧放宽，避免"第一帧必然没结果"
)
```

（若你倾向不引入 `min_occurrence` 参数，等价做法：窗口 <3 帧时跳过 `_filter_detections`。）

### 改动 2：延迟优化（必做，二选一；推荐 B）

- **方案 A（最快）**：`WINDOW_SIZE` 10 → **3**，并把 `min_occurrence` 固定为 1
  - 预期窗口满时约 1.5~2 s；代价是跟踪连续性下降（画面间可能跳）
- **方案 B（推荐）**：**只对最新帧做检测 + 分割**，跟踪只在检测失败时复用上一帧掩膜
  - 即不再对整窗口重跑；窗口仅用于保存最近帧供 SAM2 传播用
  - 预期单帧稳定 < 1000 ms，且不随会话增长劣化
- 不改接口：以上只影响内部计算范围

### 明确不做（本指令范围外）

- 不改任何响应字段/错误码/HTTP 路径
- 不改 ASR（A2）链路
- 不改 `scripts/**` 现有引擎（只能 import 复用，或在我们同意后改）
