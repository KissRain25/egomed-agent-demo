## 二、范围（不做什么）

- ❌ 不改任何接口（字段/路径/错误码；契约 v1.0.1 冻结）
- ❌ 不做 WebSocket 推送（N7 待定）、不做 AR 镜片渲染、不做多目标来回切换的复杂对话

## 三、架构与文件结构

```
client/live_client.py
├── FrameSource（抽象）            read() -> (ok, frame)  |  release()
│   ├── VideoFileSource            视频文件/帧目录（M1 自动化用）
│   ├── WebcamSource               cv2.VideoCapture(0, CAP_DSHOW)
│   └── GlassesSource              占位：眼镜 SDK 到位后实现（回调→内部队列→read()）
├── compress_frame(frame)          numpy 帧 → jpg bytes（参数与 mock_client 一致）
├── FramePump（发送线程）          抽帧 → 压缩 → post_frame → 更新 last_overlay
├── Display（回显）                原帧 + overlay 叠加 + 状态文字（中文用 PIL 绘制）
└── main()                         CLI 参数 → 启动 → 循环 → 退出清理 → 落盘报告
```

**主循环只依赖 `FrameSource.read()`** —— 这是"眼镜到位只换适配层"的落地方式（`决策记录.md` D2/D7）。

## 六、关键设计决策（本计划内定，无需再讨论）

| 决策 | 定法 | 理由 |
|------|------|------|
| 发帧节奏 | 默认 **5 fps**，`--fps` 可调 | 服务端 200~500ms/帧；发更快只会被 latest-wins 覆盖，白耗带宽 |
| 网络阻塞 | 发送放**后台线程**（并发=1，新帧到来时丢旧帧，不排队） | 阻塞主循环会把采集拖到 2fps；与契约"丢帧语义"一致 |
| 显示策略 | 主线程 `cv2.imshow` + `waitKey(1)`；overlay 为空时**保留上一帧结果直到新结果到达** | 医生看到的是"最近一次有效分割"，不闪跳（D4） |
| 显示叠加内容 | 原帧 + overlay 半透明叠加 + 左上角状态（FPS/延迟/目标名/提示语） | 单窗口自证性能，便于录屏与观察 |
| 坏帧处理 | 客户端不自行判定坏帧，**以服务器返回为准**（`overlay==""`） | 单一真相源在服务端，客户端只做展示策略 |
| 会话生命周期 | 启动生成一个 `session_id`，退出即结束；`--session` 可指定复用 | 与契约"一次医生使用过程一个"一致 |
| 分辨率与压缩 | 采集请求 1280×720；压缩后与 `mock_client` 规格一致 | 契约第 2 节 |
| 眼镜适配 | 抽象 `FrameSource`；眼镜 SDK 回调 → 内部队列 → `read()` | 换硬件只改一个类 |

## 七、风险与对策

| 风险 | 触发信号 | 对策 |
|------|---------|------|
| 摄像头被其他程序占用 | `cap.read()` 持续返回 False | 报错提示关闭会议软件；`--probe` 逐个试 index 0~3 |
| 无桌面会话/无法弹窗 | `cv2.imshow` 报错 | `--no-show` 无头模式（仍落盘帧），验收不依赖窗口 |
| 中文提示乱码 | putText 显示方块 | 用 PIL 绘制（字体 `C:\Windows\Fonts\msyh.ttc`） |
| 摄像头实际帧率低于预期 | 有效帧率 <5 | 降低分辨率至 960×540 或降 `--fps` |
| GPU 显存/并发冲突 | 服务端 OOM 或延迟飙升 | 保持发帧 5fps、并发=1；必要时服务端降 int8（需李，走授权） |
| 麦克风无权限/无设备 | `sounddevice` 打开失败 | 降级为播 `cmd_03.wav` 验证链路（M4 降级方案） |
| 光线不足（室内） | 画面过暗，服务器判坏帧 | 提示开灯；这本身是坏帧语义的正确表现，不算 bug |
