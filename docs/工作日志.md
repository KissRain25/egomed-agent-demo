**N37 远场语音门槛（☑）—— 既让远处的声音听得见、又不再被噪声误触发**

- 背景：失败案例 7 是「环境闲聊被 ASR 编成器官序列」；眼镜麦克风是**远场**的，只会更严重。原 VAD 只判"有没有块超阈值"，敲键盘/关门都能触发一次 A2。
- 做法：`MicListener` 加**四道门槛**（阈值都用实测数据标定）

| # | 门槛 | 参数（默认） | 判别依据（实测） |
|---|------|------|------|
| ① | 活跃占比 | `--mic-min-active-ratio 0.25` | 一句话里"超阈值时长"占比太低 → 噪声 |
| ② | 能量裕度 | `--mic-margin 1.5` | 峰值需 ≥ 判定阈值×1.5（贴边触发多是噪声） |
| ③ | 峰均比 | `--mic-contrast 2.5` | 人说话 **4.0~7.9**，持续噪声（空调）仅 **1.37** |
| ④ | 连续发声 | `--mic-min-active-sec 0.30` | 敲击是孤立单块（最长连续 **0.10s**），人说话必然连续成串 |

- 配套修正三处（都是实测发现的真问题）：
  1. 噪声底从"前 10 块取 **max**"改为 **30 分位** —— 原逻辑在"一开口就说话"时把人声当噪声底（实测 cmd_07 被估到 0.0833）
  2. 自适应阈值**下限 0.003 → 0.0012** —— 远场人声峰值仅 ~0.003，旧下限根本听不到；**正因为有了四道门槛，才敢把门槛降下来**
  3. 活跃占比的分母只统计"句内"（含 ≤0.25s 短暂停顿），**不把结句等待的 0.8s 静音算进去**（否则人话被稀释，实测 cmd_05 被误拒）
- **测试基础设施（也是交付物）**：`scripts/make_noise_samples.py`（可复现合成：稳态噪声 / 敲击 / 喧哗 + 远场指令 -20dB）；`scripts/vad_regression.py`（离线回放全部样例、按期望自动判 PASS/FAIL、支持 `--legacy` 对照）
- **实测：11 例 11/11 PASS，退出码 0**

| 对照 | clicks（敲击） | voice_far（-20dB） | 8 条指令 |
|------|--------------|-------------------|---------|
| 改动前（四道门槛全关 / 旧 0.003 下限） | **1 段（误触发）** | **0 段（听不到）** | 8/8 |
| **N37 之后** | **0 段（拒绝：最长连续仅 0.10s）** | **1 段 ✓** | 8/8 |

## 2026-11-03：服务端 ↔ 客户端 **字段一致性**实测（抓到并修掉一处真不一致）

- **起因**：闫问「现在服务端和客户端互通性怎么样，字段一致吧」。
  这种话不能靠"看代码挺像"来答 —— 于是做**三方对照 + 实测**。
- **三方对照**（用 grep/Select-String 扫源码得到硬数据）：
  | 一侧 | 字段 |
  |---|---|
  | 契约 §4 A1 响应 | **11 个**：status / session_id / timestamp / modality / target / overlay / message / need_confirm / candidates / elapsed_ms / frames_processed |
  | 契约 §4 A2 响应 | **8 个**：status / session_id / text / target / modality_hint / need_confirm / candidates / message |
  | 服务端实际返回 | A1 11 / A2 8（**唯一例外见下**） |
  | 客户端代码实际会读 | 成功响应 **9 个**（status / modality / target / overlay / message / need_confirm / candidates / elapsed_ms / text）+ 503 分支 2 个（state / retry_after_s） |
- **抓到的不一致（真问题，已修）**：**空文件（边界 1）分支只给 9 个字段**。
  根因：`_boundary1_payload()` 被 `post_frame` **提前 return** 调用，
  绕过了统一补 `elapsed_ms` / `frames_processed` 的那段（其它所有分支都走统一流程）。
  客户端虽然不读这俩字段，但**契约 §4 的 A1 响应是 11 个字段**，
  诊断工具/第三方客户端按契约实现就会对不上。
  修法：`_boundary1_payload(session_id, frames_processed)` 补齐两字段（`elapsed_ms=0`，本帧未跑推理）；
  为拿到 `frames_processed`，把 `_get_session()` 提到读文件之前（空帧说明会话已开始，建记录合理）。
- **新增 `client/test_field_alignment.py`**（把"一致"变成可复跑的实测结论）：
  - **契约字段清单从 `docs/API_CONTRACT.md` 的 A1/A2 JSON 示例里解析**，不硬编码 → 契约改了脚本自动跟随，不漂移；
  - 实测**每条分支**的真实响应键集合，逐条比对：缺字段 / 多字段 / **私有字段泄漏**（`_timing`/`_wait_ms` 之类）；
  - 再比对「客户端读的字段服务端是否都给」（= 有没有断链）；
  - 覆盖 5 条假实现分支 + 5 条真引擎分支 + 503 响应体。
- **实测结果**：**10/10 PASS**（假实现 M1~M5、真引擎 R1~R4、503 静态核对）。
  mock 与真引擎**两条路径的字段集合完全一致**，且与契约逐字段对齐。
- **顺带发现（不是不一致，是"给了但没人用"）**：服务端给了 `session_id` / `timestamp` /
  `frames_processed` / `modality_hint`，**客户端一个都没读**。
  其中 `modality_hint`（A2 建议模态）和 `frames_processed`（帧计数）是有信息量的，
  客户端目前只用 A1 的 `modality`；**要不要用起来是客户端的活**，本轮没动。
- **护栏**：①`client/test_server_contract.py` 的 K5 补断言「A1 空文件 11 字段齐全」（原来只查关键字段，正是它漏掉了这次的不一致）；
  ②字段对齐脚本接入 `run_regression`（mock 套件后自动跑，汇总多一行 `field-align`，可 `--skip-contract` 一并关）。
- **回归**（接入后全量跑）：mock **8/8** + contract **12/12** + field-align **6/6** + real **11/11** 全 PASS。
