## D1. 接口契约先行，验收后冻结（2026-09-10 ~ 09-19）

- **背景**：两人并行开发，方向一旦漂移就是双倍返工
- **选项**：A 先各写代码、边写边对；B 先把字段/错误码/语义全部写死再开发
- **选定**：**B** —— 契约 v0.1→v0.2 拍板 → 假实现联调 → 返工复验 → v1.0 冻结
- **理由**：返工成本随阶段递增；字段先冻结，客户端可先于真引擎完工（T5 早于 T7）
- **代价**：前期花约 2 天讨论字段，收益是联调期只有 1 轮返工
- **重新评估**：若后续要做 WebSocket/流式（A4），届时开 v1.x 而非改 v1.0

## D2. 眼镜端零智能，计算全部在服务器（2026-09-19）

- **背景**：眼镜未采购，型号未知；算力与功耗未知
- **选项**：A 眼镜端做部分推理（省带宽）；B 眼镜端只采集/压缩/发送/回显
- **选定**：**B**
- **理由**：任何型号的眼镜都能接；模型升级不动眼镜端；眼镜端代码量小（适配层 ≤200 行）
- **代价**：带宽与延迟依赖网络（局域网内实测 238ms，可接受）
- **重新评估**：若真眼镜算力强且网络差（如院区 WiFi 不稳），再考虑端侧轻量预处理

## D3. 本期只做 A1/A2 两条链路（2026-09-10）

- **背景**：契约初稿列了 4 条链路（含状态查询、WS 推送）
- **选定**：只做 `POST /frame`（画面）+ `POST /audio`（语音），A3 状态查询与 A4 WS 推送暂缓
- **理由**：A1 响应已带回模态/目标/提示，客户端自存状态即可；两条链路已构成完整闭环
- **代价**：暂无推送能力，客户端需轮询式发帧
- **重新评估**：N7 视实测延迟决定

## D4. 坏帧语义：返空 overlay + 客户端保留上一帧（2026-09-16 裁决）

- **背景**：医生转头/遮挡时画面无效，服务器 YOLO 检测不到目标
- **选项**：A 返回错误码让客户端处理；B 返回空结果 + 提示语
- **选定**：**B** —— `status=ok`、`overlay=""`、`modality=""`、`target=""`、`message="请对准屏幕"`
- **理由**：这不是故障而是正常输入，不应报错吓医生；空 overlay 让客户端保留上一帧，画面不闪跳
- **代价**：客户端必须实现"空 overlay 保留上帧"分支（N5 验收项）
- **重新评估**：若未来要求"坏帧也给出低置信度结果"，需新增字段（v1.x 兼容新增）

## D5. 并发丢帧语义：latest-wins 覆盖，而非排队（2026-09-18 落地）

- **背景**：5 并发请求曾因全局锁串行排队达 8.75s，画面积压失去实时性
- **选项**：A 排队逐个处理（结果全但不实时）；B 队列=1，新帧覆盖旧帧
- **选定**：**B** —— 实测并发 5 帧总耗时 238ms
- **理由**：医学影像辅助看的是"当下画面"，过期帧的结果无意义
- **代价**：少数帧被丢弃（符合契约第五节丢帧语义）
- **重新评估**：若某场景需要逐帧留档，再加旁路保存而**不改**主链路语义

## D6. ASR 优化必须配套幻觉防护（2026-09-19）

- **背景**：medium + 领域提示词 + hotwords 解决了谐音（1/8→8/8），但让 cmd_02 陷入复读循环（8.8s+、乱码）
- **选项**：A 保留原配置接受 7/8；B 降级回 small；C 保留优化 + 加防护层
- **选定**：**C** —— 三层防护（解码侧抑制/复读检测/时间兜底）+ 降级重试 + 返空串
- **理由**：谐音优化是刚需，防护是它的"刹车"；宁可让医生重说一遍，也不能把编造文本交给 NLU
- **代价**：极端情况下返回空串（需上层提示重说）；多一层代码复杂度
- **重新评估**：换更大模型或 fine-tune 后，可放宽阈值（保留检测作为兜底）

## D7. 无眼镜阶段用模拟替代，接口冻结保障可迁移（2026-09-19）

- **背景**：眼镜采购未定，但导师要求"暂时模拟一下情况，软件开始尝试做起来"
- **选定**：摄像头 + 桌面窗口模拟；采集/显示做成适配层，接口不变
- **理由**：把"硬件未到"从阻塞项变成非阻塞项；真机到位只换适配层
- **代价**：模拟环境与真机体验有差距（视角稳定性、抖动、光照）
- **重新评估**：眼镜到位后按实际型号调整（见 `端到端流程设计.md` §5）

## D8. 协作方式：单文件单负责人 + 指令式派活（2026-09-19）

- **背景**：两人协作曾因同时改文档产生冲突；李不主动提出变更，只按指令行动
- **选定**：每个文件唯一负责人（`server/**` 归李，`client/**`、`docs/**` 归闫）；给李的活一律**指令式**下发（改什么文件 + 跑什么命令验收），不用开放式提问
- **理由**：避免编辑冲突；指令式避免"等待对方回复"造成阻塞，冻结决策由单点发起
- **代价**：闫需承担全部接口/文档决策与验收
- **重新评估**：若团队扩到 3 人以上，改为分支 + PR 流程

## D11. N4 验收指标口径修正：把"客户端节奏"与"服务端能力上限"分开（2026-09-28）

- **背景**：`live_client.py` 的 M1 原判据是"有效发帧率 ≥ 80% 目标 fps"。但"有效发帧率 = 实际发送/时长"的上限由**服务端单帧耗时**决定（并发=1 时 ≈ 1/延迟）：实测 X 光 456ms → 上限 2.19 fps、ACDC MRI ~1.7s → 上限 ~0.6 fps。于是只要 `--fps 3~5`，**无论客户端做得多好都必然 FAIL**——判据把"服务端推理速度"当成了"客户端指标"，属于**口径错误**，不是"阈值太严"。
- **伴随 bug（真因之一）**：收尾等待写成 `while sent < submitted`，而被新帧覆盖丢弃的帧**永远不会被发送** → 每次都白等到 `timeout+1` 上限，把 elapsed 撑大约 40%，进一步压低所有速率指标（实测 6s 定时运行被记成 10.1s）。
- **选项**：A 直接调低阈值凑过（**否决**：这是"为过测试放宽标准"，红线 8）；B 修正口径 + 修 bug，并新增"是否达到服务端能力 80%"的判据。
- **选定**：**B**。改后判据：
  - **M1 提交节奏 ≥ 80% 目标**（纯客户端指标，不受服务端影响）
  - **M2 结果刷新率 ≥ 80% × min(目标, 1/均值延迟)**（在服务端能力范围内不额外损失）
  - 报告里同时给出"服务端上限≈x fps"，让读数的人一眼看懂瓶颈在服务端
- **代价**：判据从 1 条变 2 条，报告稍长；`--fps` 语义更明确（是"提交节奏"而非"完成率"）。**实时性目标没放松**——M2 的 P95 < 3000ms 与"刷新率达标"仍然把体验兜住。
- **实测**（2026-09-28，真引擎 X 光）：提交 **2.72/3 fps**（达标）、刷新 **2.13 fps（上限 2.19）**、overlay 非空 **32/32**、P95 **485ms** → 全绿。修正前同配置：M1 报 1.36 fps FAIL。
- **重新评估**：若将来服务端上真流式（A.5 P2），单帧耗时降到 200ms 量级 → 上限升到 ~5 fps，届时可直接把 `--fps 5` 作为常态并保留同样两条判据。

## D12. 坏帧判定阈值归一化：先定尺度，再定阈值（N16，2026-09-28）

- **背景**：假实现 `_is_bad_frame` 用 Laplacian 方差判"模糊/噪点"。该指标是**高频细节总量**，数值随像素总数变化。实测同一张 ACDC 正常帧：原图 lapvar **28** → 判"画面模糊"；客户端压到长边 1280 后 **136.6** → 判"正常"。**同一画面两种结论**，取决于"图有多大"。mock 套件恰好全走压缩图，8/8 通过掩盖了它（2026-09-21 登记为 N16）。
- **选项**：A 只调高旧阈值（否决：只是把交点挪走，换分辨率又会崩，且会漏掉真正模糊的小图）；B **判定前把长边归一化到固定尺寸，再按归一化尺度重调阈值**；C 换指标（如归一化梯度能量/频谱斜率）——收益不确定，成本高。
- **选定**：**B**，归一化长边 **640**（缩小用 INTER_AREA 保真、放大用 INTER_LINEAR 平滑）；阈值按新尺度重调：`mean ≥ 15`、`std ≥ 20`、`120 ≤ lapvar ≤ 12000`（界线取在坏帧与正常帧的中间地带：模糊样例 ≤18.8 / 正常帧 ≥463；噪点样例 110k / 正常帧 ≤1538）。
- **理由**：不改变判定维度（仍用同样 4 个统计量），只是把"尺度"这个隐式前提显式固定；归一化后阈值才有统一物理含义，日后换摄像头/分辨率不必重新调参。
- **代价 / 新边界**：长边 <640 的图需放大后再算，细节已被降采样抹平 → 噪点样例（480/320）会被判正常、个别正常帧（320）判"模糊"。现实链路恒 ≥640（客户端压到 ≤1280、摄像头 720p~2400px），且该分支行为**保守**（提示"请对准屏幕"而非给错结果），可接受。
- **实测**：区间内（长边 ≥640）**15/15 样本、每样本 5 个变体，判定一致且正确**；原图直发假实现坏帧 **5/5**、正常帧 **5/5**（含 2304×1728、2400×1800）；mock 套件 **8/8**。备份 `server/api.py.bak-0928-n16`。
- **重新评估**：若将来接入低分辨率采集源（<640 长边，如旧式内窥镜 640×480 以下），需改为"按实际尺度缩放阈值"或对放大路径单独放宽模糊阈值。

## D13. 误检面积过滤阈值改按模态区分（N18，2026-09-28）

- **背景**：引擎的误检面积过滤默认 `min_area_ratio=0.001`（帧面积 0.1%）。**CT 腹部（Amos）有大量小器官**，实测检出框占帧面积比：主动脉 0.011%、胃 0.014~0.069%、肾 0.034~0.048%、膀胱 0.044%，脾脏标注 0.028% —— 默认阈值会把 **27/28 个框**当误检丢弃（脾脏 0/8 检出）；其余四模态最小 0.17%（息肉），不受影响。
- **选项**：A 全局降到 0.0001（否决：会让已验证的心脏/肺/息肉也失去过滤保护）；B **按模态设阈值**；C 关闭过滤（否决：失去防误检能力）；D 改为"相对目标期望尺寸"的自适应阈值（需要目标尺寸先验，收益不确定）。
- **选定**：**B** —— 在服务端建 `MIN_AREA_RATIO_BY_MODALITY = {"Amos (CT 腹部)": 0.0001}`，其余用 `DEFAULT_MIN_AREA_RATIO = 0.001`；参数由服务端传给引擎 `_segment_target`，**引擎代码不动**（符合红线 4「不改现有引擎」）。0.0001 ≈ 20×20 px @4MP，仍能滤掉亚 20px 的碎点。
- **理由**：小器官只出现在 CT 腹部这一类模态，阈值是**模态级属性**而非全局常量；改动最小、可回退、对其他模态零影响。
- **代价 / 已知遗留**：① 阈值仍是"绝对面积比"，若将来出现更小的目标（如肾上腺 0.0xx%）还需再调 → 自适应阈值留待需要时做；② **样例集缺口**：`data/samples/amos` 内容为肾/胃/肝，**帧内并无脾脏/十二指肠**，所以此前 N8-2 记录的"Amos 0/12 检出"部分属**样例内容问题**而非全部由过滤造成（两者是不同原因，勿混为一谈）；补小器官样例帧会影响已记录的指标基线，暂未改。
- **实测**：

## D14. 网络流（手机 IP Webcam）断流自动重连（N4.5 现场暴露，2026-09-28）

- **背景**：N4.5 现场用手机 MJPEG 流当"眼镜镜头"时，采集在 **20.7s 后"采集源结束"**——但同一地址用 urllib/浏览器仍能正常取帧：**cv2.VideoCapture 读 MJPEG 不会自动重连**，手机 app 切后台/重连、WiFi 抖动任意一次断流就终止整场采集。
- **选项**：A 不处理（演示中途断流即结束，现场最尴尬）；B 断了让用户手动重启；C **客户端自动重连**。
- **选定**：**C**。参数：`max_retry=3` 轮 × 2 后端（FFMPEG → ANY），退避 0.4~2s；**打开超时 2s、读取超时 3s**（不设超时时死地址要 ~20s 才失败，重试几次就像"卡死"——实测把死地址退出耗时从 39.7s 降到 26.3s）。
- **实测**（本地 MJPEG 测试源，不依赖手机）：模拟断流后 `read()` **0.58s 恢复**、恢复后连续 **5/5** 帧正常；死地址 **优雅返回 False**（不抛异常、不死循环）；报告新增 **"网络流重连次数"** 字段便于发现手机端抖动。
- **代价**：若流真的断了，客户端会等待约 30~40s（3 轮 × 2 后端尝试）才结束采集并打日志；**不做无限重连**（避免无人值守时永远挂着）。
- **重新评估**：若真眼镜 SDK 自带重连/心跳机制，则改为依赖 SDK，本逻辑退化为兜底。

## D17. N48 帧级模态自动识别的接入方式与阈值取值（2026-11-04，N48）

- **背景**：契约 §5.3 早就要求"每帧做模态分类 + 连续 3 帧一致才切"，附录 A.10 **P1.5** 一直挂 v1.x；
  而仓库里 `models/imaging_modality_classifier.pt`（19.9MB）**早就存在、全仓库零代码引用** ——
  典型的"**资产在、功能没接**"。本轮决定把它接进去。
- **必须如实说明的一点**：该权重的训练数据是 `yolo_cls_tool_selection`（**工具选择**分类器），
  **是否等同论文里的"帧级模态分类器"不能默认等同** —— 对外材料要按"现用分类器是工具选择分类器，
  论文口径需另建/对齐"来写，**不要含糊带过**。
- **决策**：
  1. **不新增任何响应字段**，只扩展 `modality` 的取值来源（已设目标 → 语音目标反推；未设目标 → 自动识别）。
     自动识别结果**只是给医生看的提示**，不参与分割决策 → **判错不影响分割正确性**。
  2. **阈值取 0.85**（实测确定，不拍脑袋）：离线评测 599 帧 / 672 病例 —— 纯影像帧判对 **100%**（置信度 ≥0.94）；
     Montgomery 里 **18.7%（28/150）是"手机拍屏幕"的实拍照片**，被**系统性误判成 MRI**（置信度 0.46~0.84）；
     把输入分辨率从 224 提到 640 **仍然全判 MRI**（纯影像帧置信度反而 0.99→0.67）
     → 说明是**缺这类训练样本**、不是分辨率问题。取 0.85 → 这批全部转成"判不出"，**误判率 0%**，
     代价是 7% 的帧不显示模态提示（判不出无害）。
     **原则：宁可不说，也不能说错**（误导医生的代价比少一句提示大得多）。
  3. **只在"未设目标"时启用**：已设目标时模态由语音目标决定，不再跑分类器 → 省一次推理、**零影响主链路**。
  4. 分类器**默认走 GPU**，且 `classify()` 全程用 `_cvd_guard()` 还原 `CUDA_VISIBLE_DEVICES`：
     ultralytics 的 `select_device()` 在 **CPU 模式**下会把它置空，而 torch 只在**首次初始化 CUDA 时**读一次
     → 同进程里其它模块（分割链路）的 GPU 推理会全部抛 `Invalid device id`
     （本次实际踩到，见工作日志"踩坑 1"）。
  5. **任何异常一律降级为"判不出"**（权重缺失 / 加载失败 / 推理异常）—— **绝不允许分类器故障把 A1 打成 500**。
- **代价与遗留**：① "手机拍屏"这类实拍输入**目前判不出**（要补训练样本，调阈值解决不了）；
  ② 该权重与论文口径的对应关系需在论文里写清；③ 已设目标时不再重新识别模态 →
  医生换了片子但忘了重设目标时模态不会自动切换（**保持原行为**，不新增意外切换）。

## D18. N50 延迟优化的取舍：只做"不动精度"的优化，降精度手段留待拍板（2026-11-04）

- **背景**：A1 五模态 P95 ≈500~622ms（**客户端往返**口径），目标 <400ms。
- **方法：先量后动** —— 在**服务端调用侧**加细粒度分段计时（用运行时探针注入，
  **引擎源文件 `scripts/demo/egomed_demo.py` 与 `scripts/egomed_agent/*.py` 一行未改**），
  客户端 `client/eval_latency.py --detail` 出"各段耗时占比表"。
- **实测结论**：
  1. CPU 侧只有两处可省 —— 换模态首帧的**模型现场加载**（预热全 5 模态后"模型加载"段**归零**）、
     热路径上的 **prune**（Windows 上 unlink **76ms/帧、占 14%** → 改成"固定文件名覆盖写 + 引擎用干净子目录"后**归零**）。
  2. **剩余瓶颈是 GPU 计算本身**：cProfile 显示 `Tensor.to()` **183ms/轮 = 等 GPU 的同步点**（不是 CPU 计算），
     GPU 侧是 YOLO 检测 + SAM2 ViT + mask decoder → **CPU 侧已无可省的**。
- **决策**：
  1. 本轮**只做零精度代价的优化**；**降精度手段**（YOLO `imgsz` 1024→640）**不擅自做**
     —— 必须附 Dice 对照并**由负责人拍板**（"用精度换速度"是价值判断，不是技术判断）。
  2. **精度验收用"与基线逐位一致"的标准**：在线 Dice 0.396 / 0.567 / 0.301 / 0.346（均值 **0.403**）
     与 2026-09-25 基线**完全一致**，差值 **0.000**（远严于"下降 ≤0.02"）。
  3. **口径纪律**：目标是**客户端往返** P95，与服务端自报 `elapsed_ms` **不是一回事，两者都要记**
     （不拿服务端自报数字冒充端到端）；**测延迟前必须腾空 GPU**（外部程序占用会让 ASR 从 0.6s 拖到 88~144s）。
  4. **SAM2 `init_state` 复用**（省 15~30ms/帧）属"要动引擎"的改动，本轮**不做**；
     要动必须先 A/B 实测 + Dice 对照（子代理评估：复用 inference_state 有 `cached_features` 残留风险，
     漏清会**静默产生错 mask**）。
- **代价**：CAMUS 402ms / PolypGen 426ms 仍略高于 400ms（测量波动 ±30ms），
  要稳定进 400ms 需再动精度或引擎；**这一点如实记入遗留，不写"已达标"**。
