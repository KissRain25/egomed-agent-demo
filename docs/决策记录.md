## D1. 接口契约先行，验收后冻结（2026-09-10 ~ 09-19）

- **背景**：两人并行开发，方向一旦漂移就是双倍返工
- **选项**：A 先各写代码、边写边对；B 先把字段/错误码/语义全部写死再开发
- **选定**：**B** —— 契约 v0.1→v0.2 拍板 → 假实现联调 → 返工复验 → v1.0 冻结
- **理由**：返工成本随阶段递增；字段先冻结，客户端可先于真引擎完工（T5 早于 T7）
- **代价**：前期花约 2 天讨论字段，收益是联调期只有 1 轮返工
- **重新评估**：若后续要做 WebSocket/流式（A4），届时开 v1.x 而非改 v1.0

## D2. 眼镜端零智能，计算全部在服务器（2026-09-19）

- **背景**：眼镜未采购，型号未知；算力与功耗未知
- **选项**：A 眼镜端做部分推理（省带宽）；B 眼镜端只采集/压缩/发送/回显
- **选定**：**B**
- **理由**：任何型号的眼镜都能接；模型升级不动眼镜端；眼镜端代码量小（适配层 ≤200 行）
- **代价**：带宽与延迟依赖网络（局域网内实测 238ms，可接受）
- **重新评估**：若真眼镜算力强且网络差（如院区 WiFi 不稳），再考虑端侧轻量预处理

## D3. 本期只做 A1/A2 两条链路（2026-09-10）

- **背景**：契约初稿列了 4 条链路（含状态查询、WS 推送）
- **选定**：只做 `POST /frame`（画面）+ `POST /audio`（语音），A3 状态查询与 A4 WS 推送暂缓
- **理由**：A1 响应已带回模态/目标/提示，客户端自存状态即可；两条链路已构成完整闭环
- **代价**：暂无推送能力，客户端需轮询式发帧
- **重新评估**：N7 视实测延迟决定

## D4. 坏帧语义：返空 overlay + 客户端保留上一帧（2026-09-16 裁决）

- **背景**：医生转头/遮挡时画面无效，服务器 YOLO 检测不到目标
- **选项**：A 返回错误码让客户端处理；B 返回空结果 + 提示语
- **选定**：**B** —— `status=ok`、`overlay=""`、`modality=""`、`target=""`、`message="请对准屏幕"`
- **理由**：这不是故障而是正常输入，不应报错吓医生；空 overlay 让客户端保留上一帧，画面不闪跳
- **代价**：客户端必须实现"空 overlay 保留上帧"分支（N5 验收项）
- **重新评估**：若未来要求"坏帧也给出低置信度结果"，需新增字段（v1.x 兼容新增）

## D5. 并发丢帧语义：latest-wins 覆盖，而非排队（2026-09-18 落地）

- **背景**：5 并发请求曾因全局锁串行排队达 8.75s，画面积压失去实时性
- **选项**：A 排队逐个处理（结果全但不实时）；B 队列=1，新帧覆盖旧帧
- **选定**：**B** —— 实测并发 5 帧总耗时 238ms
- **理由**：医学影像辅助看的是"当下画面"，过期帧的结果无意义
- **代价**：少数帧被丢弃（符合契约第五节丢帧语义）
- **重新评估**：若某场景需要逐帧留档，再加旁路保存而**不改**主链路语义

## D6. ASR 优化必须配套幻觉防护（2026-09-19）

- **背景**：medium + 领域提示词 + hotwords 解决了谐音（1/8→8/8），但让 cmd_02 陷入复读循环（8.8s+、乱码）
- **选项**：A 保留原配置接受 7/8；B 降级回 small；C 保留优化 + 加防护层
- **选定**：**C** —— 三层防护（解码侧抑制/复读检测/时间兜底）+ 降级重试 + 返空串
- **理由**：谐音优化是刚需，防护是它的"刹车"；宁可让医生重说一遍，也不能把编造文本交给 NLU
- **代价**：极端情况下返回空串（需上层提示重说）；多一层代码复杂度
- **重新评估**：换更大模型或 fine-tune 后，可放宽阈值（保留检测作为兜底）

## D7. 无眼镜阶段用模拟替代，接口冻结保障可迁移（2026-09-19）

- **背景**：眼镜采购未定，但导师要求"暂时模拟一下情况，软件开始尝试做起来"
- **选定**：摄像头 + 桌面窗口模拟；采集/显示做成适配层，接口不变
- **理由**：把"硬件未到"从阻塞项变成非阻塞项；真机到位只换适配层
- **代价**：模拟环境与真机体验有差距（视角稳定性、抖动、光照）
- **重新评估**：眼镜到位后按实际型号调整（见 `端到端流程设计.md` §5）

## D8. 协作方式：单文件单负责人 + 指令式派活（2026-09-19）

- **背景**：两人协作曾因同时改文档产生冲突；李不主动提出变更，只按指令行动
- **选定**：每个文件唯一负责人（`server/**` 归李，`client/**`、`docs/**` 归闫）；给李的活一律**指令式**下发（改什么文件 + 跑什么命令验收），不用开放式提问
- **理由**：避免编辑冲突；指令式避免"等待对方回复"造成阻塞，冻结决策由单点发起
- **代价**：闫需承担全部接口/文档决策与验收
- **重新评估**：若团队扩到 3 人以上，改为分支 + PR 流程

## D9. 新增依赖 sounddevice 用于真实麦克风采集（2026-09-20）

- **背景**：N4.6 要演示"真人说话 → 识别 → 分割"的对话交互；环境内无任何音频采集库，也无 ffmpeg 可绕开
- **选项**：A 不加依赖，播预录 `cmd_03.wav`；B 装 `sounddevice`；C 装 `pyaudio`
- **选定**：**B** —— `sounddevice 0.5.6`（含 cffi），经闫授权安装
- **理由**：跨平台、回调式 API 干净（音频块由驱动主动推送）；比 pyaudio 安装更省事；体积小
- **代价**：环境多一个依赖（已记录）；回调式与摄像头轮询式机制不同，代码里需两套采集节奏
- **重新评估**：若真眼镜 SDK 提供音频采集接口，则改为直接调用 SDK，去掉该依赖

## D10. A.10 P1/P2 backlog 处置结论（2026-09-28，N11）

- **背景**：契约附录 A.10 有 P1×4 / P2×4 遗留项（2026-09-16 联调时登记），此后项目已完成 N13（延迟）、ASR 幻觉防护等，需重新评估每项的现状与去留。
- **处置结果**：

| 项 | 内容 | 处置 | 理由 |
|----|------|------|------|
| P1.8 | 窗口模式单帧 6546ms 超预算 | ✅ **已解决**（N13） | 窗口 10→1 只推理最新帧，A1 P95 ≈500ms（远超 §5.6 目标） |
| P1.6 | 1002 会话不存在触发路径 | ✅ **关闭（本期不做）** | 服务端自动建会话，1002 永不可达；补触发需加 query 参数（动接口）→ 挂 v1.x |
| P1.7 | 2003 目标无法确定触发路径 | ✅ **关闭（已由 need_confirm 表达）** | 跨模态歧义已实测触发（“左心室”→候选 [LV cavity, Left Ventricle]）；2003 码保留为扩展位 |
| P1.5 | §5.3 帧级模态分类 + 3 帧防抖未实现 | ◐ **挂 v1.x（附启用条件）** | 引擎存在分类器权重 `models/classifier/imaging_modality_classifier.pt`（20.8MB，**当前未下载、无代码引用**）。现流程“语音定目标→目标反推模态”已满足主流程；**启用条件**：产品需要“无语音时自动识别模态”或需要防模态抖动时，按“下载权重 → 帧级分类 + MODALITY_SWITCH_N=3 防抖 → 接入服务端”实施（约 0.5~1 天） |
| P2.9 | A1 `timestamp` 应为 `int` 必填 | 🔧 **待服务端小修** | 当前 `Optional[str]` 且未使用；改 3 行，属契约合规度提升（需授权） |
| P2.10 | `overlay` 未压缩（长边 ≤1280/q80） | 🔧 **待服务端小修（优先）** | 实测真引擎 overlay base64 达 **723KB~1.28MB/帧**；按契约压缩后约 150~200KB → 带宽与解码耗时降 5~6 倍（5fps 下约 5MB/s → ~1MB/s）。**N11 里性价比最高的一修** |
| P2.11 | `/healthz` 非契约接口未报备 | ✅ **正式登记为辅助接口** | 现已被 `launch_sim_glasses.py`、`eval_latency.py` 等工具依赖（用于预热判据/探活）；登记为“非契约运维探活接口（白名单）”，不改主契约 |
| P2.12 | `frames_processed` 并发下语义偏差 | 📝 **登记，随 P2.10 一起修** | 现为“响应时刻计数”而非“该帧处理完计数”；语偏差小，与 P2.9 同批处理更省事 |

- **选定**：先做文档层处置（本决策）；服务端三项（P2.9/P2.10/P2.12）作为**一个小修包**，待闫授权后由 AI 实施（备份 + 登记 + 通知李），或写成指令下发李。
- **代价**：P1.5 不做 → 无语音时系统不能自动判断模态（当前依赖医生先说话，符合产品设定）；P2.10 不修 → 带宽/解码开销偏大（局域网可接受，公网不可接受）。
- **重新评估**：① 产品需要“自动模态识别”时启用 P1.5；② 若眼镜端走公网/4G，P2.10 从“建议”升为“必须”。
